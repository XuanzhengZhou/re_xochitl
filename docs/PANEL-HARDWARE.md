# rM2 屏幕（EPD + 软件 TCON）完整模型

> 本文取代 `ZSPLASH.md` 里关于帧几何/命令位的部分。
> 证据等级：**[实测]** 本机硬件验证 · **[官方]** 官方二进制/源码 · **[推理]** 未直接验证

---

## 0. 一句话

rM2 **没有 EPDC**。面板是被 i.MX7D 的 **LCDIF 当成一块被动矩阵点阵屏**在扫：
每来一个像素时钟，SoC 往 24 位并行总线上送一个 `{8 bit 命令, 16 bit 驱动码}` 字；
面板侧只是移位寄存器 + 源极/栅极驱动，**所有波形时序都是用户态软件按帧喂出来的**。
所以"刷新时间 = 相位数 × 帧周期"，没有别的魔法。

## 1. 硬件链路

```
xochitl ──画 8bit 灰阶──> /dev/shm/swtfb.01 (1872×1404×2 B)
                              │
                        SWTCON 编码器（xochitl 内部，普通用户态）
                              │ 写 32bpp cell
                              ▼
                        /dev/fb0 (mxs-lcdif)
                              │ LCDIF 24 位 RGB dotclk 模式，40 MHz
                              ▼
                    ED103TC2 面板（1872×1404，TTL 并行，40-pin FPC）
```

- 内核 `mxsfb` 带 rM2 私有补丁：`Driver set to prevent frying pan mode`。
- `/proc/fb` 只有 `0 mxs-lcdif`；`epdc@306f0000` 在 DT 里是 disabled。
- 触摸设备 `pt_mt` 报 `min X 0..1403 / min Y 0..1871` → 面板 **1404 × 1872**。

### 1.1 汇流排只有 22 条数据线 **[官方]**

`lcdifgrp` 的 `fsl,pins` 只有 27 个 pad = **22 数据 + CLK + DE(ENABLE) + HSYNC + VSYNC + RESET**。
少的不是一根，是两根数据线被 mux 成 GPIO：

| 引脚 | mux 成 | 用途 |
|---|---|---|
| `LCD_DATA16` (mux 0x108) | ALT5 GPIO3_IO21 | `regulator-gdoe` EN（Gate Driver Output Enable）|
| `LCD_DATA22` (mux 0x120) | ALT5 GPIO3_IO27 | `regulator-sdoe` EN（Source Driver Output Enable）|

**这正好解释了命令字节的固定位**：观测到的命令只可能是
`0x41/0x43/0x45/0x47/0x51/0x53/0x61`，全部满足 **bit0=1、bit6=1**
——而 bit0/bit6 恰好落在 DATA16/DATA22 上，被面板侧常量拉高。
有效命令位只剩 **bit5..bit1**（6 条线）。**[推理，高置信]**

## 2. 帧几何（这是之前最容易错的地方）

```
pan buffer 一行  = 面板的一列（1404 列）
行内一个 cell    = 面板的 8 个像素行（8 consecutive panel rows）
一行 260 cell    = 26 命令 cell + 234 内容 cell
234 cell × 8 px  = 1872 px  ← 正好面板高度
pan buffer 1408 行 = 4 preamble 行 + 1404 内容行
```

面板坐标 ↔ 用户坐标（两轴都翻转）：

```
panel_col = 1403 - user_x
panel_row = 1871 - user_y
```

一个 cell（4 B，小端）：

| 位 | 含义 |
|---|---|
| `[15:0]` | 8 个面板行的 2 bit 驱动码，lane K → bit `(7-K)*2` |
| `[23:16]` | **8 bit 命令字** |
| `[31:24]` | 不传输（24 位总线只送低 3 字节） |

驱动码：**`0` = 不驱动，`1` = 推黑，`2` = 推白**。

### 2.0 ⚠️ 写 cell 必须用 32 位读改写（本项目最大的坑）

`/dev/fb0` 的 mmap 是 **write-combining** 映射。按 4 字节步长写 **2 字节**
（`memcpy` 半个 cell、`uint16_t` store、`strh`）会被写合并缓冲**静默吞掉**：

```c
/* ✗ 完全无效，读回看着是对的，但面板毫无反应 */
memcpy(buf + (4+pc)*1040 + 26*4, codes, 468);

/* ✓ 唯一可靠写法 */
uint32_t *l = (uint32_t*)(buf + (4+pc)*1040);
for (int s = 0; s < 234; s++)
    l[26+s] = (l[26+s] & 0xFFFF0000u) | codes[s];
```

这个坑曾经让"逐像素渲染"的全部尝试静默失效（读回比对完全一致，
但屏幕一个像素都不动），而"整行统一填码"因为天然是 32 位写所以一直正常，
于是现象看起来像"只能刷纯色，一画图就不行"。

**规则：永远不要用 `memcpy`/半字刷新往 fb 里写 cell；要么 32 位读改写，
要么整字 `volatile uint32_t` 拷贝。**

**[实测]** 修好之后，官方 INIT（111 帧刷白）+ 按图像推黑 502,120 个暗像素
（40 帧）= 屏幕上出现白底 + 黑页眉条 + 22 行黑正文，几何/坐标完全正确。

### 2.1 两种布局

| 布局 | xres | 行距 | yres | 内容 cell | 谁用 |
|---|---|---|---|---|---|
| 260 cell | 260 | 1040 B | 1408 | **26..259** | 官方 kernel / xochitl |
| 334 cell | 334 | 1336 B | 1405 | 73..306 | U-Boot zplash |

两者内容宽度都是 **234 cell = 1872 px**，缓冲区**不能混用**。

## 3. 命令字模板（官方，逐字节） **[官方 + 实测吻合]**

官方不是查表，而是用位掩码逐位 OR/BIC 出来的（xochitl `0x5644e4` / `0x564640`）：

```
fill_first_line (pan buffer 第 0 行):
   全行 = 0x0043_0000
   cells 20..142  |= 0x0004_0000     -> 0x47
   cells 40..102  &= ~0x0002_0000    -> 0x45

fill_line (其余行):
   全行 = 0x0041_0000
   cells 8..18    |= 0x0020_0000     -> 0x61
   cells 55..254  |= 0x0002_0000     -> 0x43
   cells 26..259  |= 0x0010_0000     -> 0x53 / 0x51   (仅内容行)
```

展开后（260 word/行）：

| 行 | 命令分布 |
|---|---|
| 0 | `0..19:43  20..39:47  40..102:45  103..142:47  143..259:43` |
| 1,2 | `0..7:41  8..18:61  19..54:41  55..254:43  255..259:41` |
| ≥3 | `0..7:41  8..18:61  19..25:41  26..54:51  55..254:53  255..259:51` |

**`0..25` 是 26 个纯命令 word，`26..259` 是 234 个内容 word。**

关键事实：**xochitl 只在初始化时写命令位，之后永不重写**（生成器唯一调用者
`buildShadow 0x564b44`，只有 4 个调用点：上电三帧 data=`0000/5555/AAAA` +
打开 `/dev/fb0` 建影子帧缓冲）。⇒ **命令字节不是局部刷新快慢的原因。**

## 4. 像素编码

相位表按 `(prev, tgt)` 二维索引，16 级灰阶：

```c
idx   = (prev << 4) | tgt;        /* prev/tgt 都是 0..15，15 = 白 */
code  = T[idx];                   /* 0 / 1 / 2 */
cell  = OR over lane K of (code << ((7-K)*2));
```

- 逐相位写 cell 的**低 16 位**，高 16 位命令位保持不动（volatile u16 写）。
- 变更跟踪缓冲初始化成 `0xFF`（= 灰阶 15 = 白），因为上电后面板是白的。
- 局部更新 = `partial` 表（把 `idx` 对角线 `src==tgt` 清零 → 不变就不驱动）。

## 5. 时序

| 布局 | htotal | vtotal | pixclock | 帧周期 |
|---|---|---|---|---|
| 260 | 263 | 1553 | 28800 ps（34.72 MHz）| **11.76 ms** |
| 334 | 337 | 1408 | 25000 ps（40 MHz）| **11.86 ms** |

- `FBIOPAN_DISPLAY` **真的阻塞一个帧周期** **[实测 10.8–11.6 ms/次]**。
- `fbiopan` 的 `yoffset` 就是槽号 × yres；`CUR_BUF` 跟着走。
- `prevent_frying_pan` 补丁让 ioctl 立刻返回剩余 jiffies（永不 0），但**仍然等 VSYNC**。
- ⇒ 一个相位 = 一次 pan = 一个面板帧。**没有任何"缩短一帧"的手段**：
  LCDIF 有 MPU/8080 智能模式、BUSY 握手、AXI 限流，但**没有暂停/停点时钟档位**；
  缩 `yres` 只会把内容平铺（面板栅极扫描是它自己的），拉高 pixclock 会欠驱动。

## 7. 21 ms 局部刷新的真相 **[官方]**

不是门线掩码，不是拉高时钟，而是**换了一张更短的波形表**：

```
/usr/share/remarkable/speedy-gonzales.csv
每行 4 个逗号字段：  mode , current , target , 相位串
   mode / current / target : 0..15 十进制
   相位串 : 只含 '0' '1' '2' 的字符串，一个字符 = 一帧 = 一个相位
```

**想 2 帧就写 2 个字符** → 2 × 11.76 ms ≈ 23 ms ≈ 观测到的 21 ms。

读取链：`EPSwtcon 构造 0x55324c` → `loadCsvTable 0x5563b0` → `parseCsvFile 0x55f7dc`。

**这台机器上没有这个文件**，所以走 `.wbf` 回退（A2 最少 10 相位、DU 12 相位），
自然拿不到 21 ms。放进一个合法 CSV 就能拿到任意长度的自定义波形。

## 9. 自己能驱动了（全部实测通过）

`wr2.c` + `panel/wbf_bands.bin` 是完整参考实现。当前能力：

| 能力 | 实测数据 |
|---|---|
| 整屏 GC16 16 级灰阶 | 46 相位, 编码 435 ms + 播放 539 ms |
| 整屏 A2 单色（快） | 12 相位, 编码 113 ms + 播放 133 ms |
| 局部刷新（DU，只编脏列） | 脏列 310/1404 → 编码 6.4 ms + N×11 ms |
| 首帧上电 INIT | 111 帧 / 1.32 s（只在开机后第一次更新时需要）|

### 9.0 **决定性结论：波形的每个相位必须恰好占一个帧周期**

这是整件事的根因，也是本轮唯一的"顿悟"。

之前 `full`（GC16 46 相位）一直白屏 + 残影，而 `page`（同一组 code1 重复 40 帧）
正常工作。当时的错误结论是"逐帧变化的 cell 数据不驱动"。真实原因是：

> `play()` 用「读-改-写」把相位写进 fb：
> `l[26+s] = (l[26+s] & 0xFFFF0000u) | code;`
> 对 write-combining 内存，每个 cell 变成一次读 + 一次写 → **写满一个槽要 30 ms**。
> 30 ms = 2.5 个帧周期，于是**每个相位被展示了 3~6 帧**，波形被整体拉长，
> GC16 的电荷平衡和 settle 全部失效。

改成「RAM 里建好整槽模板 + 纯 32 位整字拷贝」后写入降到 **1.94 ms/槽**，
每相位严格 1 帧 → GC16 立刻正确出图，16 级灰阶也正常。

**[实测]** 同一份代码、同一份波形表，只改写入方式：

| 每相位实际时长 | GC16 结果 |
|---|---|
| 34 ms（编码 27 + 写 6）| 全白 + 残影 |
| 11.7 ms（预编码 + 1.94 ms 写入）| ✅ 白底 / 黑标题条 / 22 行黑字 / 底部 16 级灰阶全对 |

推论（写驱动必须遵守）：
- 每相位时长必须是 `1/frame` 的整数倍，**且最好是 1**；
- 因此编码必须快于一帧（现在 9.4 ms < 11.76 ms，达标）；
- 因此不能"边播边编"，要么预编码进 RAM，要么保证编码 < 一帧。

### 9.1 排除掉的几个错误假设（都有实测）

| 假设 | 怎么验的 | 结论 |
|---|---|---|
| WC 丢数据 | 3 种图案写满整槽，经 `/dev/mem` 旁路回读 | **0 格不符**，WC 没问题 |
| `pan()` 不换地址 | 直读 LCDIF `CUR_BUF`(0x40) | 每次都换，步长正好一个槽 `0x165800` |
| `pan()` 不 vsync 同步 → 撕裂 | 线程高频轮询 `CUR_BUF` 记录改变时刻 | pan 先等 8.8 ms 到 vsync，**再**写地址，写完立刻返回 → 切换在帧边界，不撕裂 |
| 逐帧变化的内容不驱动 | 四象限分四段依次推黑，每段 24 帧 | **四象限按顺序全黑** → 换帧完全正常 |
| wbf LUT 索引方向反了 | 4 条横带各用一种索引约定/相位方向 | 四种都是全白 → 不是索引问题 |
| 棋盘图案本身有问题 | 同棋盘用纯 code1 推 24 帧 | ✅ 清晰棋盘 → 数据通路正常 |

### 9.2 LCDIF 真实寄存器布局（修正之前的表）

之前以为 `CTRL` 在 `0x10`。实际是 **每个寄存器占 0x10 字节，`+4/+8/+12` 是
`SET/CLR/TOG` 别名**（读回都返回同一个值，很容易误判）：

| 偏移 | 寄存器 | 实测值 |
|---|---|---|
| `0x000` | `CTRL` | `0x000a0f21` |
| `0x010` | `CTRL1` | `0x01070500` |
| `0x020` | `CTRL2` | `0x00a00000` |
| `0x030` | `TRANSFER_COUNT` | `0x05800104`（1408 行 × 260 cell）|
| `0x040` | `CUR_BUF` | 随 `pan()` 变，基址 `0xa9d00000` |
| `0x050` | `NEXT_BUF` | `0xab358000`（= 基址 + 16 槽，常量）|
| `0x060` | `TIMING` | `0` |
| `0x070` | `VDCTRL0` | `0x11300001` |
| `0x080` | `VDCTRL1` | `0x00000611` = 1553 = vtotal |
| `0x090` | `VDCTRL2` | `0x00040107` → htotal 263, hsync 1 |
| `0x0a0` | `VDCTRL3` | `0x00020002` |
| `0x0b0` | `VDCTRL4` | `0x00040104` → 260 \| SYNC_SIGNALS_ON(bit18) |

`fb0` 的 `fix.smem_start = 0xa9d00000`，`smem_len = 33,554,432`，`line_length = 1040`，
`yres_virtual = 23936`（17 槽）。

### 9.3 面板的驱动强度曲线（`ladder` 实测）

8 条竖条分别给 1/2/3/4/6/8/12/20 帧纯 code1：

| 帧数 | 1 | 2 | 3 | 4 | 6 | 8 | 12 | 20 |
|---|---|---|---|---|---|---|---|---|
| 视觉 | 几乎不可见 | 极淡 | 可见 | 浅灰 | 中灰 | 深灰 | 近黑 | 全黑 |

用户确认："左白到右黑，共 8 条"。所以 **帧数 ≈ 灰度**，且前后两端都存在明显的
死区/饱和区。这条曲线是设计刷新策略（尤其局部刷新帧数）的唯一依据。

### 9.4 局部刷新：机制与实测

从 wbf 解出 DU/A2/DU4 的相位结构（这才是"快刷"的本质）：

| 模式 | 黑←白 | 白←黑 | 不变 | 相位数 | 时长 |
|---|---|---|---|---|---|
| DU | `1`×24 | `2`×24 | `0`×25 | 25 | 292 ms |
| A2 | `1`×11 | `2`×11 | `0`×12 | 12 | 141 ms |
| DU4 | `0`×4 `1`×24 | `0`×4 `2`×24 | `0`×29 | 29 | 340 ms |

也就是说 **DU/A2 根本不"成像"，只对真正改变极性的像素定向推 N 帧**。
官方 21 ms 的局部刷新 = 2 帧；按上面的曲线，2 帧只能得到很淡的变化 —— 这是
"快刷"的固有代价，不是实现问题。

**[实测]** `pupd`：整屏 GC16 建立基线后，把 200×150 的黑块沿 x 逐步移动，
每步只编码脏列窗口：

| 指标 | 数值 |
|---|---|
| 脏列窗口 | 310 / 1404（22%）|
| 编码 | **6.4 ms** |
| 播放 24 帧（DU 满幅）| 268 ms |
| 播放 2 帧（官方快刷量级）| **约 22 ms** |

用户确认："只有一个干净黑块，没有拖尾"。

**踩到的坑**：`prv`（上一帧状态）必须**每一步**同步更新。只在整轮结束时同步，
会导致"旧位置回白"那一步查到 `tgt==prev`，DU 判为无变化 → 零驱动 → 擦不掉，
屏幕上留下一条黑带。

### 9.5 温度档（正确性必需）

面板温度来自 `/sys/class/thermal/thermal_zone0/type == epd-thermal`
（另有 `/sys/class/hwmon/hwmon1/name == sy7636a_temperature`，文件是 `temp0`）。
本机实测 21 °C → band 7（21..23）。

温度边界 `[0 3 6 9 12 15 18 21 24 27 30 33 38 43 48]`，共 14 档。
各模式相位数随温度变化：

| 模式 | 各档相位数 |
|---|---|
| INIT | 149 133 117 103 89 159 135 111 99 87 79 71 63 59 |
| DU | 73 65 57 50 43 37 31 25 22 19 17 15 13 12 |
| GC16 | 131 116 102 90 77 66 55 46 38 38 38 38 38 38 |
| A2 | 35 31 28 24 21 17 15 12 10 10 10 10 10 10 |
| DU4 | 84 75 65 58 49 42 35 29 24 24 24 24 24 24 |

`panel/wbf_bands.bin`（327,908 B）已生成全部 14 档 × 4 模式（DU/GC16/A2/DU4），
相位去重后 1263 行 × 256 B。格式：

```
"MXWF" | u16 ver | u8 nband | u8 nmode | u16 npool
u16 bounds[nband+1] | u16 nph[nmode*nband]
u16 rows[sum(nph)]  | u8 pool[npool][256]
模式顺序 0=DU 1=GC16 2=A2 3=DU4；phase_row = pool[rows[base_sum+ph]]

注意 **两个区长度不同**：`nph` 区固定 `nmode*nband*2` 字节（本例 112），
`rows` 区是 `sum(nph)*2` 字节（本例 4428）。写载入器时把前者写成后者，
会让所有相位指向同一行 —— 现象是"每相位编码结果完全相同"。
```

已逐字节核对：blob 的 band 7 与原先编译进 `wbf_lut.h` 的表 **46/25/12/29 相位全部一致**。

### 9.6 写一个真驱动需要什么（结论）

```
1. 打开 /dev/fb0，FBIOPUT_VSCREENINFO 设 260×1408, yres_virtual 17×1408,
   pixclock 0x7080, margins 1/1/1/143（得到 htotal 263 / vtotal 1553 → 11.76 ms = 85 Hz）
2. 在 RAM 里建一块 1.46 MB 的模板槽（命令字节固定），运行时只改内容 cell
3. 上电后第一次更新前跑一次官方 INIT（111 帧，净零驱动）
4. 维护 prv（当前屏上状态）与 img（目标）；每次更新算 key = (tgt<<4)|prv
5. 读温度选 band，取波形；预编码全部相位到 RAM（每相位 < 一帧）
6. 逐相位：整槽 32 位拷到 fb → pan(0)；每相位恰好一次 pan
7. 局部刷新：只编脏列 + 只播 N 帧；每步都要 memcpy(prv, img)
```

严格禁止：
- 对 `/dev/fb0` 做 `memcpy` / 半字等非 32 位整字访问（会静默丢数据）；
- read-modify-write 是合法的，但慢 15 倍，且会把相位拉长 >1 帧 → 波形失效；
- 让任何一个相位占用超过一个帧周期；
- **更新结束后把最后一帧留在 fb 里**（见 9.7）。

### 9.7 **每次更新结束必须留一帧全 0（无驱动）**

这是第二个致命陷阱，且极其隐蔽。

`wr2` 退出后 `LCDIF` 仍在 `RUN` 状态，会**永久不停地扫描 `CUR_BUF`**。
也就是说最后一帧会被**无限重复驱动**，屏幕会被这一帧的码慢慢推到位，
把前面 44 个相位的效果全部覆盖掉。

**[实测]** `gscale`（16 级阶梯，46 相位）第一次跑出来是
"白底 + 只有左边第 2 条黑竖条" —— 那正好是**最后一相位的 code1 区域**。
补上两帧全 0 之后立刻变成正确的 16 级阶梯。

正确做法：每个更新序列的最后写入一帧「所有内容 cell 的 16 位码 = 0」（无驱动），
再 `pan` 一次。code 0 不驱动，e-ink 双稳态，画面自然保持。
之后哪怕 LCDIF 扫一万年也不会再动面板。

### 11.2 wbf 文件格式（C 端实现所需的最小集）

```
[0x00] u32 checksum        (CRC32 over file[4:file_length]，初值 CRC32("\0\0\0\0"))
[0x04] u32 file_length
[0x0E] u16 fpl_lot         ← 面板批次，决定文件名里的 R###
[0x10] u8  mode_version    ← 模式名序列的版本（0x19 → INIT,DU,GC16,GL16×3,A2,DU4）
[0x11] u8  wf_version  [0x12] u8 wf_subversion   ← 文件名里的 AF<ver><sub>
[0x17] u8  frame_rate      (0x85)
[0x1C] u24 xwia            ← 字符串块地址
[0x20] u24 wmta            ← 模式指针表地址
[0x24] u8  luts   [0x25] u8 mc   [0x26] u8 trc
[0x30] u8  bounds[trc+2]   ← 温度边界，末位是上界   然后 1 字节校验
[xwia] u8 len + len 字节字符串 + 1 字节校验
       → 形如 "320_R355_AF0A11_ED103TC2U2_VB3300-KCD_TC"
         取 "AF…" 字段的下一个字段 = TFT_VID
[wmta] 每个模式一个 {u24 addr, u8 cs}
       在每个模式的 addr 处再放 trc+1 个 {u24 addr, u8 cs}（每温度档一个）
       每个档 addr 指向一张 RLE 压缩的波形表
```

**表解码（RLE）**：读字节 `c`；
- `0xFC` → 翻转 RLE 开关（其后是原样字节）；
- `0xFF` → 结束，下一个字节是累加校验和；
- RLE 开：再读 `len`，输出 `len+1` 个 `c`；
- RLE 关：直接输出 `c`。
展开长度 ÷ 256 = 相位数（luts=0x04 → 32×32 LUT，每相位 256 字节）。

### 11.3 面板指纹：官方从哪读，本机是什么

**[实测]** strace 官方 xochitl：

```
openat("/dev/mmcblk2boot1", O_RDONLY) = 5      ← barcode 就在这个分区
openat("/usr/share/remarkable/320_R402_...C5.....wbf")   ← 逐个试
openat("/usr/share/remarkable/320_R351_...U2.....wbf")
openat("/usr/share/remarkable/320_R355_...U2.....wbf")
openat("/usr/share/remarkable/320_R355_...U2.....wbf")   ← 命中，再次打开全解析
```

**[实测]** xochitl 自己打印的结论（这行是决定性证据）：

```
Reading waveforms from /usr/share/remarkable/320_R355_AF0A11_ED103TC2U2_VB3300-KCD_TC.wbf
```

所以本机面板指纹是 **FPL_LOT = 0x163 (=355) / TFT_VID = ED103TC2U2**。

`/dev/mmcblk2boot1` 是 2 MB，只有一个 TLV 记录区，5 条记录：

```
[0] "RM110-111-01171"
[1] "FUM211004939"
[2] "BYD210114001810"
[3] "EUFZBRBC1W1V009UBAT -1.33"
[4] "TESTS_DONE"
```

记录格式是 `<u32 BE 长度><数据>`，无字段 id。**这 5 条里没有字面量 355**，
说明官方在本机走的是回退路径，`barcode → (fpl_lot, tft_vid)` 的映射规则**尚未解出**。
`epd info` 会把这段 TLV 直接打印出来，方便以后对拍。

`epd.c` 因此采用：环境变量 `RM2EPD_WBF` > `/etc/rm2epd.conf`（`fpl_lot=`/`tft_vid=`）
> 内置已验证默认值(0x163 / ED103TC2U2) > 三级回退（仅 FPL_LOT / 仅 TFT_VID / 任选）。
本机 `/etc/rm2epd.conf` 已写入正确值，`epd info` 显示"精确匹配 FPL_LOT+TFT_VID"。

顺带：42 个 wbf 的头部 CRC32 **全部有效**，官方挑 R355 不是因为它特殊，而是因为
它是第一个同时匹配 FPL_LOT 与 TFT_VID 的文件。

### 11.4 新踩的两个坑（都很隐蔽，务必记住）

**坑 A：8bit → 4bit 的溢出**
```c
img[i] = (row[i] + 8) >> 4;    /* 错！255 -> 263>>4 = 16，超出 0..15 */
```
`kp` 是 `unsigned char`，`(16<<4)|15 = 271` 截断成 `15`，
也就是被解释成 "目标黑 / 原来白" → **整片白色背景被推成黑色**。
正确写法：`(v*15u + 127u) / 255u`。并且 `build_kp` 里对两边都 `&0xF` 兜底。

**坑 B：局部刷新前必须用当前屏上状态初始化目标图像**
`img` 是刚 malloc 的内存(全 0)。局部刷新只改一个矩形，其余像素本该保持
`tgt == prv`（DU/A2 才会判为"无变化"）。漏掉 `memcpy(img, prv, UW*UH)` 的话，
其余像素全是"目标黑" → **整列高度被推黑，出现一条竖黑带**，
而且它还会把这份错误状态写进状态文件，把后续所有更新一起带坏。
这条同时说明：`prv`（屏上状态）是驱动的一等公民，必须持久化并在每次更新后同步。
