# zplash（官方波形引擎）在用户态跑起来了

> 纯内存实验，**全程没有向 `/dev/fb0` 写一个字节、没有一次 pan**。

---

## 0. 结论

**官方那个 19 KB 的波形引擎（`zplash`）可以在 Linux 用户态直接加载并调用。**
这是路线 R（复用官方波形、彻底脱离 xochitl）成立的前提，现在它成立了。

代价是三处小改动，我已经验证过：

| 改动 | 原因 | 做法 |
|---|---|---|
| NOP 掉 2 条**特权指令** | 用户态执行会 SIGILL | `0x10: mcr p15,0,r0,c1,c0,2`（写 CPACR）<br>`0x18: vmsr fpexc`（PL1-only，Linux 的 VFP 模拟器不认） |
| **重定位 97 条 `movt`** | 它不是位置无关代码 | 全部 `movt rX,#0x8030` / `#0x8031` 改成新基址 |
| 映射 **192 KB**（不是 19 KB） | 它的 bss 到 `base+0x1ffff` | `mmap` 一块 64 KB 对齐、低 16 位为 0 的 RWX 区 |

---

## 1. 加载配方（可复用的代码）

```python
raw = gzip.decompress(open("/var/lib/uboot/zplash","rb").read())   # 2,910 B -> 19,032 B
buf = bytearray(raw)
struct.pack_into("<I", buf, 0x10, 0xE1A00000)   # mcr p15  -> mov r0,r0
struct.pack_into("<I", buf, 0x18, 0xE1A00000)   # vmsr fpexc -> mov r0,r0

base = 0x60000000        # 必须 64K 对齐；低 16 位为 0 才能只改 movt
size = 0x30000
libc.mmap(base, size, PROT_READ|WRITE|EXEC, MAP_PRIVATE|MAP_ANON|MAP_FIXED_NOREPLACE, -1, 0)

# 重定位：movt 的 imm16 = 0x8030 + (off >> 16)
for 每个 movt(imm16 ∈ [0x8030, 0x803F]):
    new = imm16 - 0x8030 + (base >> 16)

memmove(base, buf, len(buf))
```

三个坑，逐个踩过：

1. `0x80300000` **超出用户空间**（这台机器是 2G/2G 切分），`mmap` 直接 `ENOMEM`。
2. 只改 `movt #0x8030` 不够——还有 **61 条 `#0x8031`**（bss 在 `base+0x14a58`），
   漏掉就会 `SIGSEGV` 写飞。所以规则要按 offset 算。
3. `vmsr fpexc` 不被 capstone 标成特权，但 Linux 的 `vfp_undef` 只模拟 FPSCR，
   写 FPEXC 一律 SIGILL。NOP 掉即可，Linux 自己维护 FPEXC.EN。

## 2. ABI 全通了

```
init_entry(&fns) = 0        ← 偏移 0 的入口，填充 5 个函数指针
  set_temp  = 0x600001bc
  clear     = 0x60000610
  fill      = 0x60000768
  init_tbl  = 0x600007f0
  blit_gc   = 0x60000814

set_temp(22)  -> 0
init_tbl(&tbl) -> phases = 111,  table = 0x60000c8c
phase table = [1×24, 0×4, 2×24, 0×5, 1×25, 0×4, 2×24, 0×4, ...]   # 只有 0 / 1 / 2
```

对上了 U-Boot 的写法：

```c
splash.fill(frame1, 0x5555);
splash.fill(frame2, 0xAAAA);
int phases = splash.init_tbl(&wf_init);
for (i = 0; i < phases; i++) mxs_pan(wf_init[i]);   // ← 111 次，在 0/1/2 三个槽之间跳
```

`frame0 = clear()`、`frame1 = 0x5555`、`frame2 = 0xAAAA`，相位数 111。**这就是每次开机跑的那段。**

## 3. 最有力的一条证据：`clear()` 复现了设备上的 idle 图案

`clear()` 写进一块 scratch 内存的内容分布：

```
0x00 : 1,407,810      0x53 : 328,680      0x41 : 85,644
0x43 :    37,968      0x61 :  16,848      0x51 :    90
```

而设备上官方 swtcon 写进 `/dev/fb0` 的那张 idle 表是：

```
0x41 / 0x43 / 0x45 / 0x47 / 0x51 / 0x53 / 0x61
```

**同一组值。** 说明 `zplash` 和 xochitl 里的 `EPFramebufferSwtcon` 是同一套引擎
（或者说同一个波形数据源）。这就把路线 R 的合法性从"推测"变成了"实测"。

顺带解开一个谜：设备上 `/dev/fb0` 的内容之所以从来不变，是因为它停在了
**`clear()` 产出的 idle 帧**上——swtcon 认为屏幕已经是干净的，没有东西要驱动。

## 4. 发现一个必须先解决的几何不匹配

引擎自己测出来的帧尺寸：

```
clear() 写入范围 = 0 .. 1,877,079  =  334 × 1405 × 4
fill(v) 的写模式  = 每 4 字节写一个 16 位值（32bpp，一像素一字）
```

**所以 zplash 是按 U-Boot 的 `334 × 1405 @32bpp` 编译的。**

而 Linux 这边 xochitl 用的是 **`260 × 1408 @32bpp`**（一页 1,464,320 B）。两者不等：

| | 宽 | 高 | 每像素 | 一帧 |
|---|---|---|---|---|
| zplash（U-Boot） | 334 | 1405 | 4 B | 1,877,080 |
| Linux fb 页 | 260 | 1408 | 4 B | 1,464,320 |

直接拿引擎的帧往 Linux 的页里塞会错行。

**解法（也是下一步）：把 fb 切回 `334×1405`。**
这不是"发明新模式"，而是 `modes` 里就列着的那一个（`U:334x1405p-84`），
也正是每次开机 bootloader 用的模式——已知能用。

约束算过了：`line_length = 334×4 = 1336`，
`yres_virtual ≤ 24,893,440 / 1336 = 18,632`，所以能有 **13 个对齐的整帧**
（`13 × 1405 = 18,265`），够 U-Boot 那套用 4 个。

## 5. 还没搞定的：`blit_gc` 的参数语义

试了 16×16 / 8×8 的 bitmap 往 `(100,100)` 画，`blit_gc` 几乎不写东西
（返回一直为 1，窗口内改动 0~16 字节）。

可能原因（待验证）：
- 它期望 **整幅面板的 bitmap**，`x0/y0/w/h` 只是裁剪区；
- bitmap 不是 1 字节/像素，而是 4bit 打包；
- 它需要"上一帧"是某种特定状态。

好在**这一块不影响主线**：INIT 序列只用到 `clear` / `fill` / `init_tbl` / pan，
全部已验证可用。`blit_gc` 是"画静态图像"要用的，属于下一阶段。

## 7. 第一次真机 INIT 重放（2026-11-07）

### 7.1 做了什么

把 fb 从 `260×1408 @34.72MHz/85Hz` 切到 **`334×1405 @40MHz`**（U-Boot 那套），
然后完全用 zplash 引擎跑 U-Boot 的 INIT 序列，**全程没有 xochitl**：

```
xres=334 yres=1405 xres_virtual=334 yres_virtual=18265 (13 整帧)
pixclock=25000(40MHz)  margins 全 1  hsync/vsync=1
stride=1336  frame=1,877,080

clear(f0)=0  fill(f1,0x5555)=0  fill(f2,0xAAAA)=0  clear(f3)=0
init_tbl -> phases=111, table 只用 slot 0/1/2
111 相位 × 2 轮 pan，最后 pan 到 idle 帧 3
```

### 7.2 屏幕表现（用户目视）

> 「变成了很多斜着的线条，像光栅一样，然后变换了一下，然后黑白闪烁一下。」

**链路全通**：引擎 → 帧 → pan → 面板，没有 xochitl 参与。
斜线 → 相位切换 → 黑白闪烁，正好对应 idle 帧 → 相位循环 → `0x5555/0xAAAA` 交替帧。

### 7.3 但暴露了一个几何问题（重要）

把 `clear()` 产出的帧按 1405×334 摊开看：

```
r0: 43 45 43 53 51 53 51 53 53 51 53 43
r1: 41 61 41 53 53 53 53 53 53 53 53 43
r2: 41 61 41 53 53 53 53 53 53 53 53 43
r3: ...（1..1404 行逐字节相同，只随列变化）
```

**帧内容只依赖列、不依赖行。** 屏幕上却是**斜条纹**。

推理：只随列变化的图案，在屏幕上呈斜线 ⇒ **每一行被水平平移了固定量**
⇒ 引擎假设的行距（pitch）和面板/LCDIF 实际扫的行距不一致。

另一条支持证据：`fill()` **不是从偏移 0 开始写的**——

```
clear() 写入范围 (0, 1877079)        ← 从 0 开始，长度正好 1,877,080
fill()  写入范围 (292, 1875633)      ← 从 292 开始，末尾少 1447 字节
```

292 = 73 个字。说明 `fill` 内部对帧原点有自己的假设（可能带左右 margin）。

### 7.4 因此需要反编译确认的三件事

已把 `zplash.bin` + 加载脚本 + 问题清单传到 home-server：
**`文档/rev-Zplash/`**（README_ZSPLASH.md 里有完整说明）。

要问的（按重要性）：

1. **行距常量**：`clear`(0x610) / `fill`(0x768) / `blit_gc`(0x814) 里
   推进一行时加多少？是不是 `334*4=1336`？还是别的常数（比如 336 字、340 字）？
2. **帧原点的偏移**：`fill` 为什么从 292 开始？是不是有 `origin = 73 字` 之类的常量？
3. **数据落在哪条字节道**：确认是 `+2`（R 通道）还是依赖 24/32bpp 的字节打包。
4. `blit_gc` 的参数语义（见 README 里的清单）。

拿到 1、2 就能算出正确的 pitch，斜线应该立刻消失；
拿到 4 就能开始画真正的图像。

## 8. 补测：帧的行结构量出来了（纯内存，无风险）

### 8.1 方法

`fill(v)` 只写"像素载荷"，不写行 padding。把一块 `0xCC` 缓冲交给它，
统计**写入偏移之间的间隙**，行距就直接暴露出来了。

### 8.2 结果

```
fill(0x5555): 写入 657,072 字节 = 1404 行 × 468 B
             行间间隙 403 B × 1403 次
clear():      写入 1,877,080 字节，从 0 到 1,877,079 连续（全帧）
```

解方程：每行载荷 `468 B = 234 字`，行距 `1336 B = 334 字`，载荷起始于**行内第 73 字**（off=292）。

```
1872 px × 4 bit = 7488 bit = 234 字  ✔ 完全对上
1336 = 73(前) + 234(载荷) × 4 + 27(后)  ✔ 无剩余
```

所以一帧的结构是：

```
1405 行 × 334 字（1336 B）
  字 0   .. 72   ← 行头（clear 会写，fill 不碰）
  字 73  .. 306  ← 234 字像素驱动载荷 = 1872 px @ 4bpp
  字 307 .. 333  ← 行尾
第 0 行内容与其他行不同（帧头）
```

**这解释了为什么 `clear()` 的行几乎逐字节相同**：它是"均匀白色"的驱动程序，
每行自然应当一样。

### 8.3 顺带确认的两件事

1. **模式切换是真的生效了**，不是假动作：

   ```
   切换前: line_length=1040   (260×4)
   切换后: line_length=1336   (334×4)
   恢复后: line_length=1040
   ```

   所以上一轮 INIT 的斜线**不是**"set_par 被跳过"造成的。

2. `smem_len` 实际是 **33,554,432（32 MB）**，不是我们一直以为的 24.9 MB。
   在 334×1405 模式下最多可放 **17 个对齐整帧**（32 MB / 1,877,080 = 17.8），
   空间比原先判断的宽裕。

### 8.4 仍待反编译回答（已给 home-server 的清单，补充这几条）

对着上面量到的数字，需要确认：

1. 行距常量是不是就是 `1336`，还是从某个字段算出来的（比如 `words_per_line * 4`）。
2. **`fill` 为什么不写前 73 字**——那 73 字是行命令/时序，还是 `clear()` 才会初始化的头部？
3. 载荷确实是 4 bit/像素、一点对应一个时钟吗？这决定"斜线是不是行进动"：
   若面板每行只吃 234 字而我们送 334 字，多出的 100 字会让画面逐行移位 → 斜线；
   若面板用 HSYNC 复位行计数则不会。**这一个问题就能定性斜线。**
4. `blit_gc` 往里写的是"载荷区"还是整行（含行头）。

## 9. 反编译结果落地：整条链路真机跑通（2026-11-07）

反编译报告在 home-server `文档/rev-Zplash/REPORT.md`（24 KB，含 Unicorn 逐字节差分验证）。
我把它落成了一个 C 程序并在真机上跑通。

### 9.1 独立复核了报告的三条关键结论

| 结论 | 我的独立验证 |
|---|---|
| 帧 = 1405 行 × 334 cell，cell 低 16 位 = 8 px × 2bit | `fill` 的写入间隙分布算出每行 234 字载荷 / pitch 1336 B，与报告一致 |
| **334 布局 content 起点 = cell 73** | zplash 自带模板里 cell 72 = `0x41`、cell 73 起 = `0x53` ✔ |
| **260 布局 content 起点 = cell 26** | 设备 idle 帧里 cell 25 = `0x41`、cell 26 起 = `0x51` ✔ |
| 22 °C = 46 相位 | 从 `zplash_tables.json` 取 band7 得 46 相 LUT，驱动码只出现 0/1/2 ✔ |

### 9.2 已经跑通的

```
C 程序：zigcc 交叉编译 -> armv7，device 上直接跑
输入：1872×1404 的 8bit 灰阶位图（棋盘格）
过程：切 fb 到 334×1405 @40MHz -> 46 相位 GC16 -> 每相位 build 一帧 -> FBIOPAN_DISPLAY
结果：**屏幕上出现了正确的黑白棋盘格，方向正立（左上=黑，右下=白）**
```

用户目视确认：*「这回变成棋盘格了」*。**这意味着 bitmap → LUT → 驱动码 → 帧 → pan → 面板，全链路正确。**

代码在设备 `/tmp/zm334.c`（本地 `/tmp/zm334.c` + `/tmp/zm334.h`）。

### 9.3 踩到的两个大坑（都很隐蔽）

**坑 1：260 模式的控制位模板是"空闲态"，不驱动面板。**

我们最初从设备 `/dev/fb0` 的 idle 帧里提取控制位（`0x41/0x43/0x51/0x53/0x61`），
拼上像素码后**屏幕上毫无反应**。换成 zplash 自带的 668 字节模板（有效帧）+
把 fb 切到 334×1405，立刻就出图了。

结论：**控制位不是纯静态的"接线信息"，它带"本帧是否驱动"的语义。**
要用 zplash 的模板，就必须用 334 布局。

**坑 2：`remux` 会自己把 rm2fb server 拉起来，`systemctl is-active rm2fb` 是假信号。**

真正要确认"没人抢屏"必须：

```sh
systemctl stop remux          # 这条才是关键
# 然后确认没有进程占 /dev/fb0
```

只停 `rm2fb.service` 时，`remux` 仍然会拉起一个带 `librm2fb_server` 的 xochitl，
它以 85 Hz 循环 pan，把我们的 pan 每 12 ms 覆盖一次 —— 现象就是"写了没反应"。

### 9.4 还没解决的：白不够白 + 残影

最后的表现：棋盘格出来了，但**白格偏灰、整体发闷，旧界面残影仍在**。

原因分析（下一步要查的）：

- 22 °C 那 46 个 LUT 里，**灰阶 15（白）在绝大多数相位拿到的驱动码是 0（不驱动）**，
  只有灰阶 0（黑）被主动推。也就是说这个波形假设"白是背景态"，
  白格最终有多白取决于**驱动前**面板是什么状态。
- 我加的 111 步清场（字节表 `[1×24][0×4][2×24]…`，用 `fill` 语义整屏推挽）
  确实跑完了，但没有把面板带到干净的白底。
- 可能原因：清场序列结束在 code 2 的推挽上，落点不是白；
  或者需要「清场 → 画图」之间留出稳定时间；或者该用另一档温度表。

### 9.5 性能实测

| 场景 | 耗时 |
|---|---|
| 46 相位整屏（334 布局） | **3.6 s**（其中编码占大头，pan 仅 ~0.55 s） |
| 46 相位整帧（260 布局） | 0.8 s |

编码是瓶颈，不是面板。报告 §13 给的路子（相位去重 −41%、常量相位走 fill、
脏矩形、换 Du/Glf 短波形）正是下一步该做的。

### 9.6 结论

> **脱离 xochitl 在技术上已经验证完毕**：我们自己的进程能完整驱动这块屏，
> 用的是官方自己的波形数据，方向正确、图像正确。
>
> 剩下的不是"能不能"，而是"好不好"：白阶基准、残影清除、编码性能。
> 这三件都是可调参数问题，不再是逆向未知。

## 10. 白底 / 灰阶 / 时序三件事一次解决（2026-11-07 真机，v2）

§9.4 那三个症状有**同一个根因**，修掉之后全部消失。

### 10.1 驱动码极性（实测确定）

| code | 效果 | 证据 |
|---|---|---|
| 0 | **不驱动** | `clear()` 产出的 idle 帧内容；翻上去屏幕不变 |
| 1 | **推黑** | 整屏 code1 ×24 帧 → 全黑 |
| 2 | **推白** | 整屏 code2 ×24 帧 → **整屏纯白，饱和**（290 ms 足够） |

这坐实了"白是背景态"的假设：**46 相位 LUT 里灰阶 15 全程拿到 code 0**，
所以"画一张白底页"这件事本身不会驱动任何像素 —— 白必须靠 code 2 主动刷出来。

### 10.2 真正的 bug：相位被拉长了 7 倍

v1 的循环是「编码一帧（**78 ms**）→ pan（13 ms）」。编码期间上一帧还在被扫描出去，
所以**每个相位实际在屏上停留 ~91 ms ≈ 7 个面板帧**。整条波形的时间轴被拉伸 7 倍，
灰阶当然出不来 —— 这不是波形表的问题。

修法：每相位只算**一行**（334 个 u32），再 `memcpy` 铺到 1405 行。

```
修复前：78 ms 编码 + 13 ms 播放 = 91 ms/相位   → 46 相位 4.2 s，灰阶糊成一团
修复后：11.6 ms/相位（= 1 个面板帧）           → 46 相位 533 ms，灰阶正常
```

**判据**：`pan()` 返回"剩余 jiffies"，串行 pan 的间隔就是面板帧周期（实测 11.6~13.3 ms）。
任何让单相位超过这个数的编码开销，都会污染波形时间轴。

### 10.3 LUT 索引是交错的

16 字节/相位**不是**按灰阶顺序排的：

```
gray g <  8  →  row[2*g]
gray g >= 8  →  row[2*(g-8) + 1]
```

按 raw 顺序读会把整条波形看错。交错映射后：

- 相位 3–20：灰阶 1–14 吃 code 2（过冲到白），灰阶 0 和 15 吃 0
- 相位 21–35：灰阶 0–14 全部吃 code 1（推到黑）
- 相位 36–44：按目标灰度给不同**长度的 code 2 尾巴**，这就是灰阶的塑形段
- 相位 45：全 0（收尾）

灰阶 5 和 6 的序列只差 2 帧 —— 所以实测上这两级**必然**粘连，是波形本身的性质。

### 10.4 v2 实测数字

| 项目 | 结果 |
|---|---|
| 极性与饱和 | code2 ×24 帧 = **290 ms** → 整屏纯白 |
| 46 相位全屏播放 | **533 ms**（11.59 ms/相位） |
| 灰阶阶梯（16 条横带） | 用户目视：**15 级以上可分辨**，仅 gray5/gray6 粘连 |
| 文档页（白底+黑页眉+30 行文字） | **底很干净，无上一张图的残影** |
| 全屏刷新总耗时 | 闪白 290 + GC16 533 = **823 ms** |
| 编码开销（带逐行内容） | 1027 ms / 46 相位（22 ms/相位）→ 需要用 scratch 预生成 + memcpy |
| 几何 | **1872×1404 精确 1:1，四周无裁切**；竖屏为自然方向 |

### 10.5 现在可用的全屏刷新路径

```
① 整屏 code2 刷 24 帧   (290 ms)   —— 把面板拉到确定白底，同时清掉上一张图
② 46 相位 GC16 播放      (533 ms)   —— 白底页之外的像素被推黑/推灰，白像素不动
```

**残影为什么消失了**：不是波形会自动擦除，是第 ① 步把面板整体重置成了白。
这反过来说明现表**不具备自擦除能力** —— 灰阶 15 永远拿 code 0。

### 10.6 仍然缺的（更新后的清单）

1. **局部刷新 / DU**：现表无前态维度，局部区域能不能只靠"矩形外填 code 0"保持不动，
   还没验证；而且没有短波形，任何更新都得走 823 ms 全屏。
2. **完整的 (prev,cur) 波形表**：在 `/usr/share/remarkable/*.wbf` 里（42 个文件）。
   §11 记这条线的进展。
3. **温度档**：真实温度源是 `/sys/class/hwmon/hwmon1/temp0`（`sy7636a_temperature`），
   **不是** `thermal_zone0`。实测 21 °C，落在 band7 [21,23]。
4. **编码性能**：带真实内容的页面编码 22 ms/相位，必须预生成到 scratch 再播放。

### 10.7 局部刷新的边界（实测，重要）

试了两种"只驱动一部分区域、其余 cell 填 code 0"的做法：

| 做法 | 结果 |
|---|---|
| **整行横带**：`y ∈ [600,800)` 全宽推白，其余行 code 0 | ✅ **干净**。标定图完好，只多了一条全宽白带，其他一处没动 |
| **行内矩形**：`x ∈ [80,400) × y ∈ [80,400)`，同一行里部分 cell 推白 | ❌ **串扰**。目标区域以外出现变化，还出现沿 cell 节距的条纹 |

**结论：局部刷新必须按整行（全宽）做，不能只驱动一行中的一段。**

可能的物理原因：一行里混合 code 0 和 code 2，源极驱动的负载/电荷平衡被打乱，
出现串扰；而整行统一驱动时不存在这个问题。控制位里 `0x53`/`0x51` 这种逐列变化的位
（只差 bit1）很可能就是源极通道的奇偶/极性配置，我们还没解出来。

这对 UI 有直接含义：**e-ink 上做局部刷新，脏区必须按"横向长条"组织**。
对文本类界面（行、段、状态栏、键盘）来说反而自然。

### 10.8 扫描窗口：看起来像答案，实测是陷阱

帧周期确实严格正比于扫描像素数（实测，`pixclock=25000`）：

| xres | yres | 帧周期 |
|---|---|---|
| 334 | 1405 | **11.86 ms** |
| 334 | 400 | 3.40 ms |
| 334 | 200 | 1.71 ms |
| 200 | 200 | 1.03 ms |
| 150 | 200 | 0.78 ms |

`pixclock` 同样线性有效：整帧 25000→11.87 ms，15000→7.25，10000→5.27。

**但缩小 `yres` 并不会缩小驱动范围 —— 内容会被平铺。**

实测：`yres=200`、窗口内画「黑/白/黑/白」四条 50 行横带，屏上出现的是
**这条带子重复了七八次铺满整屏**。说明面板门线仍然扫满 1405 行，
LCDIF 只是把 200 行的内容循环喂进去。

**`pixclock` 缩太狠会让波形欠驱动。** 实测 `pixclock=5000`（扫描快 5 倍）时，
同一张文档页变成**整片灰色 + 横向纹理**，页眉分裂成白线。因为波形脉冲宽度
是**按时间标定**的，帧周期一缩，每一相的驱动时长就跟着缩，能量不够。

**所以驱动时间的正确公式是：**

```
刷新时间 = 相位数 × 帧周期（由波形标定的帧率决定，不能随便改）
```

wbf 头里写的 `frame_rate = 133 Hz`（7.5 ms/帧）就是标定值，对应 `pixclock ≈ 15850`。
我们现在用 25000（≈84 Hz），比标定慢 1.6 倍，属于轻微过驱动但画质可接受。

**真正的局部刷新不是缩窗口，而是整帧扫描 + 只给脏区域写非 0 码**（§10.7 已验证
"整行横带"干净）。代价是时间不省。

> 结论：官方 21 ms 局部刷新的机制**仍未被我们找到**。已排除的路径：
> 缩小 `yres`/`xres`（平铺）、拉高 `pixclock`（欠驱动）。
> 剩下的候选：控制位里的门线掩码（未解）、或 21 ms 指的是输入延迟而非面板刷新。

## 11. 用官方 wbf 二维表渲染（已完成）

### 11.1 波形数据来源不再是 zplash

设备上 `/usr/share/remarkable/*.wbf` 有 42 个官方 E Ink 波形文件（每个 ~282 KB）。
解析器 `wbf.py` 已能完整解出（自检方式见 `WBF.md`）：

- 头 48 B，`mc+1=8` 个模式、`trc+1=14` 个温区、`luts=0x04`（5-bit LUT，32×32 转移）
- **每相位 256 B = 32×32 的 `[prev][cur]` 表，2 bit/格，4 格/字节**
- 目标轴映射 `dst_index = 2 × 灰阶`

zplash 那张 16 B/相位的表是**压扁版**：相位数保留了，前态维度丢了。
这就是"必须闪白预清"的根源。

### 11.2 解码规则（实测钉死）

```
idx = cur*32 + prev      （state = 2*gray）
位序 = LSB-first         code 1 = 推黑，code 2 = 推白，code 0 = 不驱动
```

验证（DU @ 21–23 °C，25 相位）：

```
白(30)→黑(0):  24×code1 + 1×code0
黑(0)→白(30):  24×code2 + 1×code0
不变:          全 0
```

**GC16 的对角线非零是设计如此** —— GC16 是"全闪刷新"，每个像素都走一遍复位周期，
所以它天然去残影；DU 才是"不变就不驱动"。

### 11.3 各模式相位数（21–23 °C）

| 模式 | 相位 | 灰阶 | 用途 |
|---|---|---|---|
| INIT | 111 | — | 上电/清场 |
| DU | **25** | 2（黑白） | 快速局部 |
| GC16 | **46** | 16 | 全灰阶刷新 |
| GL16 ×3 | 46 | 16 | 介于两者之间 |
| A2 | **12** | 2 | 最快，残影重 |
| DU4 | 29 | 4 | 折中 |

### 11.4 已跑通

`wr.c`（+ `wbf_lut.h`，从 wbf 生成的 C 表）在真机上：

```
闪白 24 帧                     281 ms
全屏 GC16 46 相位（二维表）   播放 537 ms + 编码 1323 ms
结果：白底 + 黑页眉条 + 30 行黑文字，干净
```

**任意灰度图案现在就能渲染。** 剩下的纯粹是编码性能（1323 ms 是纯 CPU 开销，
可以预生成/缓存/相位去重压下来）。

3. 各模式（DU/A2/DU4）的实际画质/残影表现未系统测
