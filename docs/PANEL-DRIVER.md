# 自己的面板驱动（Rust 版）

> 2026-11-07。**rmdev 现在不依赖 xochitl / rm2fb 了**：`src/panel/` 自己解析
> `.wbf`、自己编码波形、自己写 LCDIF 翻页。

## 为什么原来离不开 rm2fb

这台机器**没有 EPDC**（`epdc@306f0000` 是 `disabled`），上屏全靠 LCDIF 每帧串出一页
「32-bit cell 码」。这段逻辑只存在于官方 xochitl 的 `EPFramebufferSwtcon` 里，
rm2fb 是寄生在它身上调 `sendUpdate` 的——所以「server 一死，屏幕冻住而进程一切正常」
（见 `RM2FB.md`）是结构性的，不是部署脚本的锅。

现在这段逻辑在 `src/panel/` 里重写了一遍，出处是 `epd.c`（C 版，已在真机逐项验证）。

## 分层

| 文件 | 职责 | unsafe |
|---|---|---|
| `panel/wbf.rs` | `.wbf` 头/温度边界/xwi(RLE)/模式表解析、指纹选文件 | 无 |
| `panel/encode.rs` | 模板槽、命令字节、`(目标,上一帧)→2-bit 码`、cell 编码 | 无 |
| `panel/raw.rs` | 打开 `/dev/fb0`、改几何、mmap、`FBIOPAN_DISPLAY`、整字写 | **全部在这里** |
| `panel/mod.rs` | `Panel`：初始化/局部刷新/整屏刷新/状态文件 | 无 |
| `fb.rs` | 对 UI 暴露的 `put/row_mut/blit_gray/fill_rect/get/refresh` | 无 |

`main.rs`、`canvas.rs`、`chrome.rs`、`tagsview.rs` **一行都没改**——`refresh()`
的签名和行为保持不变，只是底下换成了自己的驱动。

## 三条铁律（违反任何一条都会白屏/残影）

1. **一个波形相位必须恰好占一个帧周期**（11.76 ms）。
   实测：`pan()` 会把写 fb 的时间**吸收**进等待里——`写 2.6 + 等待 9.1 = 11.76`。
   所以只要「编码 + 写 fb」不超过一帧，流式（播放的同时编下一帧）就是安全的：
   * 小块（笔迹，编码 < 1 ms）：流式；
   * 大块（编码 > 9 ms，整屏 9.6 ms/相位）：先**把全部相位编码进 RAM**再逐帧播。
   边播边编又编不完会把相位拉到 1.5 帧以上，症状是「全白 + 残影」——
   C 版和 Rust 版**各踩过一次**，两次都是这个原因。
2. **每次更新结束必须留一帧全 0（无驱动）**。LCDIF 会一直扫最后那一页。
3. **`prv` 必须和屏上实际状态同步**。`prv` 一旦比屏上"更白"，
   编码就会判成「目标=白、上一帧=白 → 不驱动」，该盖住的东西盖不住
   （工具栏的白底盖不掉笔记就是这么来的）。所以只有**一整轮波形没被新目标
   打断**才算定影、才允许 `prv = img`。

## 波形运行期间的脏区：并集，不是最新那一块

一次波形运行期间驱动的是「**从这一轮开始到现在所有落过墨的矩形并集**」。
这既不是优化也不是手感调参，是面板的物理事实：波形相位是全局推进的，
一帧里改不了已经扫出去的部分，所以这一轮里落下的墨必须留在驱动区域里
才有机会被推。

反过来做（每次 update 都把脏区缩成它自己那一小块）的症状：
写一笔时 UI 每 ~10 ms 投一块 12×12 补丁，每块墨只被驱动 1 帧就被顶掉——
DU 要 22 帧才全黑，屏上就是一条又淡又慢的线。

配套的一条：**`prepare()`（重建 `kp`）只对新到的那个 job 矩形做**，
不要对着并集做。并集很容易长到 1264×1872，重算一次 2.4 ms，帧周期就从
11.76 被顶到 16.5 ms —— 波形被拉长 40%，手感是"发肉/跟不上"。

## 写 fb 的限制

只能**整字 32 位**写（`write_volatile::<u32>`）。`memcpy`/`copy_from_slice` 可能被
编译成 64/128 位宽搬运，这块映射会静默丢掉——读回看着对，屏上不动。

`FBIOPAN_DISPLAY` 成功时返回**正数**（剩余 jiffies），判失败只能用 `< 0`。

**只写脏行无效**：帧的完整性由 TCON 保证，必须整槽写（1.46 MB，2.6 ms）。
好在 pan 会把这段时间吸收进帧周期，所以不亏。


## 状态文件

`/tmp/rm2epd.state`：裸的 `1404×1872` 字节屏上灰度，x-major
（`prv[x*UH+y]`，0 = 黑，15 = 白）。只按脏矩形增量写（`FileExt::write_at`），
不然每帧重写 2.6 MB。文件不存在 = 刚开机 → 先跑 111 帧官方 INIT 建立白色基线。

环境变量：`RM_PANEL_STATE`（换路径）、`RM2EPD_WBF`（指定波形文件）、
`RM_DU_FRAMES`（DU 只播 N 帧，默认 0 = 全部）、`RM_PANEL_TIMING=1`（打印分块耗时）。

## 怎么验

```sh
# 1) 只验驱动，不启动 UI
./paneltest          # 白底 + 左上黑方块 + 顶部黑条 + 16 级灰阶 + 右下黑方块 + 底部刻度

# 2) 出问题时分层排查

./paneldbg raw 1 24  # 绕过编码，直接推 24 帧「推黑」→ 屏应变黑
./paneldbg slot      # 读回槽 0 的字，验证写入有没有落地

# 3) 真跑
```

注意：**不要再走 `/opt/bin/rm2fb-client`**，也不要启动 `rm2fb.service`——那会把
xochitl 拉起来抢 `/dev/fb0`。

## 四个已修的 bug（都很能装）

### 1. 相位编码的偏移写错 → 笔迹永远出不来

`encode_cols_range` 的输出是「从 `out_off` 起、按 `(pc - pclo)` 紧凑排列」，
而 `one` 是按面板列**绝对寻址**的（`put_col` 读 `one[pc*CSTR..]`）。
两段式路径（`update()`）自己拷贝到 `one[pclo*CSTR..]`，所以整屏刷新没事；
但流式路径（笔迹）传了 `out_off = 0`，编出来的帧落在 `one[0..span]`，
`put_cols` 去读 `one[pclo*CSTR..]`——恰好是刚清零的那段。

结果：**每一帧推的都是"全 0 不驱动"**，一个墨点都没有。整屏正常、笔迹全无。
诊断方法是读回槽里的字：正确的相位 0 应该是 `0x00535555`（8 条 lane 全推黑），
当时读到的是 `0x00530000`。

> 探针的坑：内容 cell 26 覆盖的是 y=1864..1871，不是屏幕上方。
> `s = (UH-1-y)/8`，否则会对着一个没用到的 cell 读半天。

### 2. 脏区被缩回最新那一块 → 墨淡、慢

见上一节。改成并集后，同一支笔从"只驱动 1 帧"变成"整支笔每一帧都在推"。

### 3. 按并集重建 `kp` → 帧周期 16.5 ms（波形拉长 40%）

并集长到 1264×1872 时，`build_kp_cols` 一次 2.4 ms，帧周期从 11.76 顶到 16.5。
改成只重建新到 job 的矩形（`kp` 只取决于 `img`/`prv`，它们只在 job 里变过）。

### 4. `prv` 提前提交 → 工具栏盖不住笔记、菜单翻白

流式路径原来不管有没有被打断，退出时都 `commit()`。于是**没跑完波形的墨**
被记成"已到位"，接下来画工具栏时 `(目标=白, 上一帧=白)` → 不驱动 →
笔记原文留在屏上盖不住。现在只有"一整轮没有新目标"才提交。

## 崩溃加固

`fill_rect`/`dim`/`refresh` 全部改成 i64 裁剪。UI 在滚动到屏幕底边时会算出
`y+h` 溢出 i32 的矩形，以前直接 panic，整个进程没了、屏停在最后一帧，
看着像"卡死、导航不进去"。驱动层不该因为上层算错一个矩形就崩。

## 实测数字（band 8，24 °C）

| 操作 | 相位 | 帧/相位 | 每帧 | 端到端延迟 |
|---|---|---|---|---|
| 笔迹 `71×71 Du` | 22 | 22/22 | **11.1 ms** | ≤ 9 ms |
| 浮层 `600×720 Gl16` | 38 | 38/38 | **11.7 ms** | ≤ 0 ms |
| 笔迹 `71×64 Du`（跑 2 轮） | 22 | 44/22 | **11.6 ms** | ≤ 8 ms |
| 整屏 GC16（两段式） | 38 | 38 | 编码 522 + 播放 454 ms | — |

编码成本：整屏单相位 **9.6 ms**（加了"8 lane 同码"快路径，之前 11.7 ms）。

## 把「能跑」修成「跟官方一样」

这一轮的目标是「最终效果与官方一致、速度不低于官方」。实际做下来，瓶颈
几乎都不在波形和编码上，而在三处写错的代码；另外几处是「语义选错了」。

### 1. `clip()` 的返回值解构写反 → 矩形放大几千倍，还 panic

`clip()` 返回 `(x0, x1, y0, y1)`，`fill_rect` / `dim` 都按这个顺序解构，
唯独 `refresh` 写成了 `(x0, y0, x1, y1)`：

* `y0` 拿到 x 的右边界、`x1` 拿到 y 的边界，于是 `w = y1 - x0`、`h = y0 - x1`；
* `11×11@720,1460` 被算成从 `720,731` 起、`740×740` 的方块，面积放大 **4400 倍**；
* 越界后 `mark_pushed` 的切片起点超过终点：
  `slice index starts at 1027782 but ends at 1027728` → **panic → abort → 回库界面**。

它**间歇性**的原因：`x = 0, w = 120` 时 `x1` 恰好等于 `y`，错位后结果碰巧
正确。所以工具栏那些刷新一直看着没毛病，**越远离原点越离谱**；`x=0` 且
`y=0` 时更会 `x0 >= x1` 直接 `return`，那次刷新被整条丢掉（"写完没反应，
点一下菜单才刷出来"）。

修法：抽成 `Fb::region()`，解构改成 `(x0, x1, y0, y1)`，并加回归用例
`region_never_enlarges_the_request`（11×11 必须原样返回，越界必须裁）。

### 2. `RectF::include()` 的「首次重置」分支 → `Line.bounds` 永远是零矩形

```rust
if self.w == 0.0 && self.h == 0.0 {
    self.x = x; self.y = y;      // 重置原点
}
```

`Line::push` 对每个采样点调**两次** `include`（左上角、右下角）。第一次
`w==0` 成立就重置、算完还是 0；第二次又成立、又重置。**无论一笔有多少个点，
`bounds` 的 `w`/`h` 永远停在 0。**

日志实证（点数正常、包围盒全零）：

```
[erase] 路径 1927 点 半径框 (33,54)-(100,1590)，命中 1 条；
        候选 [(18, 625, 0.0,  0.0,  0.0, 0.0, 31.0),
              (15, 455, -204.75, 1430.82, 0.0, 0.0, 3.0),
              (18, 402, 89.99, 138.48, 0.0, 0.0, 31.0)]
```

下游症状一大片：橡皮「擦整笔」靠 `line_bbox` 求范围 → 只剩一个点，只有
橡皮正压在坐标上才命中（**荧光笔擦不掉**，它又粗又稀疏）；擦完的重刷矩形
退化成几个像素（**擦完屏上还留着**）；选区相交、缩放裁剪同理。

### 3. 脏区差分每次扫整屏 → 每笔 32 ms

`diff_pushed` 为了兜住 app 漏报的刷新，每次 `refresh` 都把 2.6 M 像素的
`plane` 和 `pushed` 比一遍：读 10.4 MB，**DDR 带宽跑满也要 32 ms**，而且跟
请求多大完全无关。app 每落一笔付一次，刷新率被压到 16 Hz。

改成在**写入口**记包围盒：`plane` 是私有字段，对外只有 `put` / `row_mut` /
`fill_rect` / `dim` / `clear` 五个写入点，每个入口 `mark_dirty` 一次，差分
只扫这块。写字时它就是那几十个像素。配套三条：

* 比较走字节视图——`&[u8]` 的 `==` 才会下沉到 `bcmp`，`&[u16]` 是逐元素循环，慢 20~50 倍；
* `put` 值没变就不记脏（浮层重绘里绝大多数像素是原地重写）；
* `fill_rect` 逐行比对，整行已是目标色就跳过。

### 4. 每帧重新分配 2.6 MB 灰度缓冲 → 缺页 146 ms

`push_rect` 原来 `mem::take` 之后把 `levels` move 进 channel，UI 下一次就得
重新 `malloc` 同样大的一块，新页第一次写要缺页：

```
改前  [pf] refresh 1404×1872@0 总 212418us = … + 推送 211445
改后  [pf] refresh 1404×1872@0 总  65862us = … + 推送  64902
```

改成面板线程用完把缓冲还回来（`back_rx` 归还通道 + 4 深空闲池）。

### 5. 波形与渲染语义的三处修正

* **笔迹用 A2 不用 DU**：DU 25 相位 ≈ 294 ms，A2 12 相位 ≈ 141 ms，二值语义
  相同（`A2 黑←白` = 推黑 10 帧，`白←白` / `黑←黑` 全 0）。
* **圆珠笔的抗锯齿灰在 A2 下不驱动**，线会散成一串点。改成 8×8 有序抖动
  （复用 `BAYER8`）把浓度折成 0/255。用有序而非随机：e-ink 上随机图案每次
  重绘都不一样，看起来是"沙沙的闪"。
* **荧光笔重绘走真灰度**（`paint_line` 里 `tex = s >= 0.999 && !is_highlighter()`），
  必须跳过抖动，否则平涂灰会变成格子——加了 `ink_hl` 标记。

### 6. 橡皮拆成两个工具

`Tool` 枚举**不能加新值**（`.rm` 里存的就是这个 u8，23 个值必须与官方一致），
所以区别放在模式标志 `chrome.erase_stroke` 上：

* **Eraser**（刷白）：只把扫过的像素擦掉，抬笔时留下一条 `Tool::Eraser` 的
  **橡皮线**。官方也是这么存的，渲染时按顺序做减法；只擦 canvas 不留线的话，
  翻页回来擦掉的东西会全部复活。
* **Erase stroke**（擦整笔）：`commit_erase` 从模型移除笔迹，`Op::Remove` 可撤销。
* 笔尾橡皮（`BTN_TOOL_RUBBER`）固定是刷白，不受菜单当前选项影响——按下时
  就把 `stroke_erase` 定死。

配套两处修正：

* 命中判断从「点到点」改成「点到**线段**」——荧光笔采样稀疏，橡皮从两个点
  中间穿过去时离任何采样点都远；`hw` 也从 `hit_width`（档位×系数，只有 2~3 px）
  改成「`hit_width` 与采样点真实宽度取大」。
* 擦除从「按覆盖率线性衰减」改成**硬擦**（`cov >= 0.5 ? 0 : old`）。线性衰减
  会留下 `old * (1-cov)` 的中间灰，A2 一帧都不驱 → 擦不掉的残影点。

### 7. 稳定性

* channel 改成**有界**（`sync_channel(8)`）+ `try_send`。无界队列里每个 job
  带一整块灰度数据（整屏 2.6 MB），画满一屏就能把内存顶爆，而 Rust 的分配
  失败是 `abort`（systemd 里看到 `status=134`，表现就是"回库界面"）。投不
  进去就把那块**重新标回脏区**、缓冲收回池里，**不记已推**——宁可晚一帧，
  也不能把没发出去的内容当成已发。
* `ExecStart` 的 `>` 改成 `>>`，崩溃现场不会再被重启冲掉。
* `repaint_rects` 的调试描边改成只 `mark_pushed` 边框像素。以前整块标记，
  一旦 `push_rect` 因越界提前 return，那块在 `pushed` 里已经等于 `plane`，
  脏区差分再也看不见它（"框一圈圈缩小、最后彻底不显示"）。

### 实测

| 指标 | 改前 | 改后 |
|---|---|---|
| `avg_flush`（app 侧一次投递） | 5000~10746 µs | **455~1889 µs** |
| `flush/s` | 个位数 | **57~133** |
| 差分一次 | 32 ms | **35 µs** |
| 一笔 refresh（`275×277`） | 62 ms | **2~4 ms** |
| 整屏 GC16 的 `推送` | 211 ms | **65 ms** |
| panic / 重启 | 每画满一屏一次 | 0 |

端到端估算：笔采样 125 Hz ≈ 8 ms + 处理 < 1 ms + 投递 < 1 ms + 首帧
≤ 11.76 ms ≈ **21 ms**。这是从链路各段加出来的，**不是**高速相机实测。

## 截图：不要用 `/tmp/rm2epd.state`

`/tmp/rm2epd.state` 里存的 `prv` **不是"屏上现在的样子"**：流式路径里
`prv` 是"上一帧的目标"（`set_rect` 用它当编码起点写进去的），只有两段式
（`RM_PANEL_TWOPASS=1`）和静置路径才把它更新成到位值；而且正常运行时它
只在 `Drop`/`flush_state` 落盘，`SIGTERM` 直接杀进程不会写。

所以截图走另一条路：

```sh
sh tools/shot.sh 名字      # kill -USR1 → 应用把 UI 平面 dump 成 PGM → 拉回来转 PNG
```

`SIGUSR1` 的处理器只置一个 `AtomicBool`，真正落盘在主循环 `tick()` 里
（`/tmp/rmdev.shot.pgm`），拿到的就是 `Fb::plane`——我们**希望**屏上显示的东西。

## 大块刷新会临时提频（`src/cpu.rs`）

`ondemand` 空闲时降到 396 MHz，整屏编码从 9 ms/相位涨到 17 ms，关机框/睡眠图
端到端 1.1 s。`framegen` 在一轮里**只要出现过 ≥ 0.7 Mpx 的 job** 就把
`scaling_min_freq` 顶到 `cpuinfo_max_freq`，轮末还原。实测关机框
1146 ms → 548 ms（帧周期 24.7 → 11.8，超帧 45/45 → 0/45）。

注意它救不了内存带宽受限的内容：睡眠图（细衬线字）提频后仍是 1100 ms、
16.4 ms/相位 —— 那片全是"混合内容 cell"，命中不了 8 lane 同码快路径。
详见 `POWER.md` §4.2。

  （> 64 个才切）。
* ~~**快写仍然略滞后**~~：已解决。笔迹用 A2，端到端 ≈ 21 ms。

  得把编码挪到独立线程（官方就是 framegen + vsync-flip 两个线程）。
* **整屏灰度的 54 ms**：`gray_to_cols` 对 2.6 M px 实测 ~21 ns/px（读 5.2 MB
  写 2.6 MB）。只影响整屏/大块刷新，手写一笔是几十像素、不到 1 µs，所以
  没继续压。真要压得动向量化（ARMv7 有 NEON）或改 `img` 的行列序。
* **端到端延迟没有实测**：21 ms 是链路各段加出来的估算。要证实得上
  240 fps 高速相机（拍笔尖和屏幕同框，数帧差），或者是官方那种硬件探针。
* 崩溃安全：`SIGTERM` 正好落在更新中间时，最后一相位会被一直扫。要加信号处理写空白帧。
* **`Tool` 枚举不能加值**：`.rm` 里存的就是那个 `u8`（23 个值与官方一致）。
  以后再加"橡皮变体"这类功能，都只能走模式标志，不能动枚举。
